# Avtoikonom Admin — E2E Automation

Playwright + TypeScript end-to-end test project for the Avtoikonom admin panel
(`dev.admin.avtoikonom.com`). Built as a practical automation exercise: not a
single test, but a small project deliberately organized the way a suite
still has to work once it's grown to hundreds of tests across many domains —
see [Scaling this project](#scaling-this-project) for the reasoning.

## What's here

Two tests, both against the Partners domain:

- **`CreatePartner`** (`tests/partners/CreatePartner.spec.ts`, tagged
  `@smoke` `@regression`) — create a new Partner with every required field
  populated → validate it was created successfully. A fast, focused signal
  on its own: if Partner creation breaks, this is the one that goes red.
- **`CreatePartnerAndUpdate`** (`tests/partners/CreatePartnerAndUpdate.spec.ts`,
  tagged `@regression`) — the full journey: everything `CreatePartner` does
  (it calls the exact same shared step, not a re-typed copy — see
  `tests/partners/support/flows.ts`), then updates **every** editable field
  on that same Partner (name included, marked `EDITED` so it's traceable in
  the UI), reloads to force a fresh backend fetch, and verifies every change
  actually persisted, field by field.

The update half stays inside the lifecycle test rather than becoming a third
standalone test, because "verify the update persisted" is only meaningful
given the Partner creation already produced in that same run — an update
test can't stand on its own without first creating (or being handed) a
Partner to update. Login isn't a third test either, for the same shape of
reason: see [Authentication](#authentication-storagestate-not-ui-login-per-test)
below.

## Install & run

Prerequisites: Node.js 18+ and npm.

```bash
npm install
npx playwright install chromium   # first time only, downloads the browser binary
cp .env.example .env              # then fill in ADMIN_EMAIL / ADMIN_PASSWORD
npm test                          # runs headed locally, headless on CI
```

Other scripts:

```bash
npm run test:headed       # explicit headed run
npm run test:ui           # Playwright's interactive UI mode — best for authoring/debugging
npm run test:smoke        # only @smoke-tagged tests — the fast subset
npm run test:regression   # only @regression-tagged tests
npm run report             # opens the last HTML report (also generated by `npm test`)

npm run typecheck   # tsc --noEmit
npm run lint          # eslint . (also: lint:fix)
npm run format         # prettier --write . (also: format:check)
```

Without `ADMIN_EMAIL`/`ADMIN_PASSWORD` set, the `setup` project fails with a
clear message and every test that depends on it is cleanly skipped — see
[Authentication](#authentication-storagestate-not-ui-login-per-test).

### Environment configuration

| Variable         | Purpose               | Default (if unset)                       |
| ---------------- | --------------------- | ---------------------------------------- |
| `BASE_URL`       | Admin panel origin    | `https://dev.admin.avtoikonom.com`       |
| `ADMIN_EMAIL`    | Test account email    | — (the `setup` project fails, see above) |
| `ADMIN_PASSWORD` | Test account password | — (the `setup` project fails, see above) |

All environment resolution goes through `config/env.ts` — the one place that
changes if this grows into named environment profiles (dev/staging/prod).
`.env` is git-ignored; `.env.example` documents the shape. Locally the
browser also launches **maximized and headed** by default (see
`playwright.config.ts`) so a run is easy to watch; CI always runs headless.

## Project structure

```

  env.ts                  centralized, typed env resolution (loads .env once)
components/                reusable UI-pattern wrappers, not tied to one page
  AntdSelect.ts             antd <Select> — single & multi, with its quirks isolated
  AddressAutocomplete.ts    Google Places Autocomplete
  ImageUpload.ts            file input + its confirm-crop dialog
pages/
  BasePage.ts               shared navigation helper every Page Object extends
  auth/
    LoginPage.ts
  partners/
    PartnersPage.ts
tests/
  setup/
    auth.setup.ts            authenticates once; see playwright.config.ts's "setup" project
  partners/
    CreatePartner.spec.ts
    CreatePartnerAndUpdate.spec.ts
    assets/
      logo.png, logo-edited.png
    support/
      fixtures.ts             the `partnersPage` fixture (domain-scoped)
      flows.ts                 shared, test.step-wrapped steps reused across this domain's specs
      testData.ts               fixture (data) builders — unique, self-describing test data
.github/workflows/
  playwright.yml            CI: quality gate → install → run → upload artifacts

eslint.config.mjs            ESLint (typescript-eslint + eslint-plugin-playwright)
.prettierrc.json
.env.example
```

Adding a second domain (say, Requests) means adding `pages/requests/`,
`tests/requests/` with its own `support/` — the same shape, next to
`partners/`, not a new pattern to invent.

## Architectural decisions

**Playwright + TypeScript.** Chosen over Selenium/Cypress for this project:
built-in auto-waiting (this admin panel is a slow, animation-heavy SPA —
manual waits would be a maintenance trap), first-class trace/video capture
for debugging CI failures without reproducing locally, and a single
`npx playwright test` covering execution, parallelism, and reporting without
extra glue.

**Domain-organized `tests/` and `pages/`, not flat directories.** Both are
split by feature area (`partners/` today; `requests/`, `users/`, `vehicles/`
... as this grows — the app's own sidebar lists them) instead of every spec
and Page Object living loose in one folder. At two tests this is invisible;
at a hundred, a flat `tests/` directory is unnavigable and `git blame`
becomes the only way to find out which team owns a given file.

**A component layer for UI patterns, not just Page Objects.** `components/`
holds three classes — `AntdSelect`, `AddressAutocomplete`, `ImageUpload` —
each wrapping a real, non-obvious Playwright interaction quirk discovered
against this app (see the comments in each file). They used to be private
methods on `PartnersPage`. The problem with that: this app's other domains
(Drivers, Vehicles, Users, ...) almost certainly reuse the same antd
`<Select>` and file-upload patterns. Without this layer, whoever builds
`DriversPage` next either re-derives these workarounds from scratch or
copy-pastes `PartnersPage`'s private methods — both are how a 1000-test
suite ends up with the same bug fixed five times in five places.
`PartnersPage` now composes these components; it no longer knows _how_ an
antd Select opens, only which field id it's dealing with.

**`BasePage`, thin on purpose.** One shared method today
(`navigateTo(path)`), because there's only one cross-page concern worth
sharing yet. It exists so that when a second one shows up — sidebar
navigation, a header/user-menu interaction, a common "wait for the app
shell to finish loading" — it has an obvious home instead of being
duplicated into every domain's Page Object as that domain gets written.

**Page Object Model, kept thin.** Each Page Object exposes _behavior_
(`login()`, `fillNewPartnerForm()`, `expectFormMatches()`), not raw locators,
so a selector change is a one-line fix in one file, not a hunt through every
spec. `PartnersPage` deliberately reuses `fillNewPartnerForm()` for both
create and full-field update, since the app itself reuses the same dialog
component for both — one place to fix if that form changes.

### Authentication: `storageState`, not UI login per test

Every test that needs to be logged in gets there through a Playwright
project dependency, not by driving the login form itself:

1. `tests/setup/auth.setup.ts` runs once, logs in through the UI (this is
   the _only_ place in the whole suite that does), and caches the
   authenticated session — cookies and localStorage — to
   `playwright/.auth/user.json` via `context.storageState()`.
2. `playwright.config.ts` declares a `setup` project matching `*.setup.ts`,
   and a `chromium` project that `dependencies: ['setup']` and launches
   every browser context with `storageState: STORAGE_STATE_PATH`.
3. `tests/partners/support/fixtures.ts`'s `partnersPage` fixture — this
   project's `@BeforeMethod` equivalent — no longer logs in at all; the
   context is already authenticated by the time any test's fixtures run.
   It only navigates to `/partners`.

This is Playwright's own documented pattern for this exact problem, and it's
the single highest-leverage change for a suite headed toward 1000 tests:
UI login is one of the slowest things a browser test can do, and repeating
it per-test turns "run everything" from minutes into hours as the count
grows. Confirmed by running the suite before/after this change: both tests
used to log in independently; now `setup` authenticates once (~5s) and both
tests share that session, run in parallel, no UI login in either one.

**Missing credentials fail loudly, on purpose — a reversal from an earlier
version of this project.** Early on, missing `ADMIN_EMAIL`/`ADMIN_PASSWORD`
made each test silently `test.skip()` itself — friendly for a reviewer
running this without real credentials, but a real footgun at scale: a
misconfigured CI secret would make the pipeline report all green while
having authenticated, and therefore run, nothing. `auth.setup.ts` now
`throw`s a clear error instead; Playwright's project-dependency mechanism
then cleanly skips every dependent test, but the run as a whole goes red,
which is the correct outcome for a broken prerequisite.

### Tagging: `@smoke` / `@regression`, per domain

Both tests carry Playwright's native tag annotation —
`test('CreatePartner', { tag: ['@smoke', '@regression', '@partners'] }, ...)` —
so subsets can run independently: `npm run test:smoke` for the fast,
must-pass-on-every-PR set (`CreatePartner` only), `npm run test:regression`
for the fuller picture (`@regression` is a superset — every `@smoke` test
is also tagged `@regression`, so the full suite always includes the fast
one), `--grep @partners` for "just this domain" once there's more than one.
At 1000 tests, running everything on every PR isn't viable; a tag
vocabulary established from test one means the CI split (fast subset on
PR, full suite nightly) is a `--grep` flag away, not a retrofit.

**Selector strategy, in priority order:** stable `id` attributes (this app
happens to expose good ones: `name-field`, `partner-type-field`, ...) →
structural/semantic HTML (`autocomplete`, `type`) → antd's own structural
classes (`.ant-select-dropdown`, `.ant-select-selection-overflow-item`) as a
last resort, and _never_ the app's own hashed CSS-module classes or visible
copy. Two concrete traps this avoided, documented in code where they bite:

- The login button's label is locale-dependent ("Sign in" vs "Логин")
  depending on session state — a text selector would be flaky across
  environments. Fixed via `form button[type="submit"]`.
- antd's `<Select>` renders a placeholder `<span>` _behind_ the real
  `<input>`; once a value is selected, the selected-value chip sits _on top_
  of that same input. Clicking by visible text hits whichever happens to be
  on top and is flagged by Playwright as a pointer-event interception either
  way — clicking the stable `.ant-select` wrapper container (see
  `components/AntdSelect.ts`) works regardless of state.

**Data-driven, self-cleaning-by-construction test data.** `testData.ts`
generates a unique Partner name/phone/contact per run
(`QA E2E Partner <timestamp>-<random>`), so parallel or repeated runs never
collide and never depend on another run's leftover data. The Partner the
lifecycle test updates is always the one it just created — see the comment
in `CreatePartnerAndUpdate.spec.ts` for the reasoning (an update that landed
on an arbitrary pre-existing record would be non-deterministic and could
corrupt data other runs rely on).

**Persistence verification, not optimistic-UI verification.** After Save,
the test forces `page.reload()` before re-checking the Partner — a fresh
fetch from the backend, not the in-memory state the UI already had. The same
principle governs _what_ gets asserted post-update: the list table doesn't
surface Type or Description, so the test reopens the (freshly re-fetched)
Edit form itself to confirm every field, not just the ones visible in the
table.

**Config over hardcoding.** `BASE_URL` and credentials come from environment
variables (`.env` locally, GitHub Secrets in CI), resolved in exactly one
place (`config/env.ts`) — never scattered `process.env.X` reads, never
hardcoded. The same suite can point at another environment by changing one
value.

**Headed locally, headless on CI, maximized window.** `process.env.CI` (set
automatically by GitHub Actions) is the single switch; no separate config
files to keep in sync.

**Debuggability & observability.** Three artifacts, captured only on
failure/retry so passing runs stay cheap: a Playwright **trace** (full
step-by-step timeline with DOM snapshots and network), a **screenshot**, and
a **video**. The reporter is `list` (live console feedback while a run is in
progress) plus `html` (the artifact a human opens afterwards) — never
auto-opening, so CI doesn't try to launch a browser and a local run doesn't
surprise you with a popup every time. `test.step()` names every phase (Log
in / Navigate / Create / Validate / Update / Validate persisted), so both the
console output and the HTML report read as a narrative, not a wall of
individual assertions — a failure points at the exact step, not just "the
test failed".

**Code quality tooling.** TypeScript `strict` (plus
`noUncheckedIndexedAccess`, which caught a real possible-`undefined` array
access during setup, and `noImplicitOverride`, which pays for itself the
moment `BasePage` gains a second subclass), ESLint (`typescript-eslint` +
`eslint-plugin-playwright` for automation-specific rules like flagging
conditional logic in tests) and Prettier. All three run as their own fast CI
job (`quality`) that gates the — much slower — `test` job, so a lint or type
error fails in seconds, not after a multi-minute Playwright run.

## Scaling this project

Everything above is sized for two tests but shaped for many more. Asked to
imagine this suite at 1000+ tests across a dozen domains, here's what's
already in place for that, and what would still need to change:

**Already built for it:**

- Domain-organized `tests/`/`pages/` — adding a domain is "copy the shape",
  not "invent a new one".
- A `components/` layer for UI patterns that recur across domains, separate
  from any one Page Object.
- `storageState`-based auth instead of UI login per test — the single
  biggest suite-runtime cost at scale, solved once.
- A tag vocabulary (`@smoke`/`@regression`/`@<domain>`) from test one, not
  retrofitted once "just run everything" stops being viable.
- `config/env.ts` as the one seam for adding named environment profiles.
- CI already gates on lint/typecheck before spending minutes on a browser
  run — that job doesn't get slower as the suite grows, so it stays a fast
  first signal regardless of scale.

**Would still need to change:**

- **API-level setup/teardown.** At 1000 tests, creating every test's
  prerequisite data through the UI (and never deleting it) doesn't survive
  contact with reality. A thin `api/` client (Playwright's
  `APIRequestContext`, reusing the authenticated session) for fast data
  setup and a cleanup registry that deletes what a test created are both
  necessary, not optional, past a certain scale — see the two points below
  for the specific instance of this in the current suite.
- **Test data cleanup.** Nothing here deletes the Partners it creates —
  fine for a one-off exercise, not for a suite run hundreds of times a day.
  I'd add a teardown step (or a scheduled job) deleting anything matching
  the `QA E2E Partner ...` naming convention past a certain age.
- **API-level persistence verification** as a faster complement to the
  current UI-reload check — `dev.api.avtoikonom.com` is visible in this
  app's own network calls.
- **CI sharding** (`--shard`) and a real smoke-on-PR/regression-nightly
  pipeline split — the tags exist; the two-job CI split into by-tag
  pipelines is the next step once there's enough tests for it to matter.
- **Fixture composition across domains** (Playwright's `mergeTests`) once
  there's more than one domain-scoped fixture file to combine.
- **Reporting built for trend/flake analysis** (Allure or similar) — the
  built-in HTML report is the right choice for a handful of specs; history
  across thousands of runs is a different problem.
- **Cross-browser/device matrix** (Firefox, WebKit, a mobile viewport) —
  intentionally out of scope here; the whole exercise runs against one real
  environment and breadth wasn't the goal of this submission.
- **Visual/byte-level assertion for the Logo field**, e.g. comparing the
  uploaded file's hash against what the persisted `<img src>` resolves to —
  the one required field this suite exercises but doesn't verify (see
  Assumptions).
- **Component-level negative/validation tests** — required-field validation
  messages, invalid phone/email formats, duplicate-name handling — this
  suite is a happy-path lifecycle by design.
- **Secrets via a proper vault** (1Password/Vault CI integration) instead
  of raw GitHub Secrets, once there's an org's worth of pipelines sharing
  them.

## Assumptions

- The "Partner" entity's required fields, as observed on `dev`: Name, Type
  (Service/Insurer), Services (multi-select), Subscription plan, Address,
  Telephone, Contact person, Description, Logo.
- "Validate that changes have been persisted correctly" means proven against
  a fresh backend fetch (page reload), not the UI's optimistic state — see
  above.
- Address and Logo are exercised (both are required fields, so the form is
  filled with real values) but not asserted field-by-field after persistence:
  Address is a free-text Places Autocomplete result with no fixed expected
  string to compare against, and Logo has no text representation to assert
  without visual diffing — a deliberate scope cut, not an oversight (see
  Scaling this project for how I'd close it).
- `dev.admin.avtoikonom.com` is a disposable QA sandbox safe to write test
  data into — the account list already contained hundreds of prior
  `QA E2E Partner ...` records when this project started, consistent with
  that assumption.
- Subscription plan is selected (first available tier on create, a different
  one on update) to satisfy the required field, but not asserted by exact
  value: every tier in this environment's seed data renders under the same
  visible label, so no assertion could meaningfully distinguish "changed" —
  documented in `PartnersPage.expectFormMatches`.

## CI

`.github/workflows/playwright.yml` runs on push/PR to `main`/`master` and on
manual dispatch, as two jobs:

1. **`quality`** — `format:check`, `lint`, `typecheck`. Fails fast, before
   spending CI minutes on a browser run.
2. **`test`** (needs `quality`) — installs Chromium (browser binaries cached
   by `package-lock.json` hash), runs the suite (`setup` project
   authenticates, `chromium` project runs both tests against that session),
   and uploads the HTML report (always) plus traces/screenshots/videos (on
   failure) as build artifacts.

It expects `BASE_URL`, `ADMIN_EMAIL`, and `ADMIN_PASSWORD` as repository
secrets — without them, `setup` fails clearly and every dependent test is
skipped, so the pipeline goes red with an unambiguous reason rather than
silently passing having run nothing.
