# Avtoikonom Admin — E2E Automation

Playwright + TypeScript end-to-end test project for the Avtoikonom admin panel
(`dev.admin.avtoikonom.com`). Built as a practical automation exercise: not a
single test, but a small, deliberately-scoped project that could realistically
grow inside a production repo.

## What's here

- **Login** (`tests/login.spec.ts`) — the page loads and renders the sign-in
  form; a valid login redirects into the app and shows the right account.
- **Partner lifecycle** (`tests/partner-lifecycle.spec.ts`) — the main flow:
  log in → navigate to Partners → create a new Partner with every required
  field populated → verify it was saved → update **every** editable field on
  that same Partner (name included, marked `EDITED` so it's traceable in the
  UI) → reload and re-fetch from the backend → verify every change actually
  persisted, field by field.

The lifecycle test is written as one continuous flow rather than split into
isolated tests, because each step is only meaningful given the state the
previous one produced — "verify the update persisted" doesn't mean anything
without the Partner this same run just created and edited.

## Install & run

Prerequisites: Node.js 18+ and npm.

```bash
npm install
npx playwright install chromium   # first time only, downloads the browser binary
cp .env.example .env              # then fill in ADMIN_EMAIL / ADMIN_PASSWORD
npm test                          # runs headed locally, headless on CI
```

Other scripts:

```bash
npm run test:headed   # explicit headed run
npm run test:ui       # Playwright's interactive UI mode — best for authoring/debugging
npm run report        # opens the last HTML report (also generated by `npm test`)

npm run typecheck     # tsc --noEmit
npm run lint           # eslint . (also: lint:fix)
npm run format          # prettier --write . (also: format:check)
```

Without `ADMIN_EMAIL`/`ADMIN_PASSWORD` set, the login-success and
partner-lifecycle tests **skip** themselves (with a clear reason in the
report) instead of failing — the login-page-renders test still runs, since it
needs no credentials.

### Environment configuration

| Variable         | Purpose               | Default (if unset)                 |
| ---------------- | --------------------- | ---------------------------------- |
| `BASE_URL`       | Admin panel origin    | `https://dev.admin.avtoikonom.com` |
| `ADMIN_EMAIL`    | Test account email    | — (tests requiring it are skipped) |
| `ADMIN_PASSWORD` | Test account password | — (tests requiring it are skipped) |

`.env` is git-ignored; `.env.example` documents the shape. Locally the
browser also launches **maximized and headed** by default (see
`playwright.config.ts`) so a run is easy to watch; CI always runs headless.

## Architectural decisions

**Playwright + TypeScript.** Chosen over Selenium/Cypress for this project:
built-in auto-waiting (this admin panel is a slow, animation-heavy SPA —
manual waits would be a maintenance trap), first-class trace/video capture
for debugging CI failures without reproducing locally, and a single
`npx playwright test` covering execution, parallelism, and reporting without
extra glue.

**Page Object Model, kept thin.** Each Page Object exposes _behavior_
(`login()`, `fillNewPartnerForm()`, `expectFormMatches()`), not raw locators,
so a selector change is a one-line fix in one file, not a hunt through every
spec. `PartnersPage` deliberately reuses `fillNewPartnerForm()` for both
create and full-field update, since the app itself reuses the same dialog
component for both — one place to fix if that form changes.

**Selector strategy, in priority order:** stable `id` attributes (this app
happens to expose good ones: `name-field`, `partner-type-field`, ...) →
structural/semantic HTML (`autocomplete`, `type`) → antd's own structural
classes (`.ant-select-dropdown`, `.ant-select-selection-overflow-item`) as a
last resort, and _never_ the app's own hashed CSS-module classes or visible
copy. Two concrete traps this avoided, documented in code where they bite:

- The login button's label is locale-dependent ("Sign in" vs "Логин")
  depending on session state — a text selector would be flaky across
  environments. Fixed via `form button[type="submit"]`.
- antd's `<Select>` renders a placeholder `<span>` _behind_ the real
  `<input>`; once a value is selected, the selected-value chip sits _on top_
  of that same input. Clicking by visible text hits whichever happens to be
  on top and is flagged by Playwright as a pointer-event interception either
  way — clicking the stable `.ant-select` wrapper container works
  regardless of state.

**Data-driven, self-cleaning-by-construction test data.** `testData.ts`
generates a unique Partner name/phone/contact per run
(`QA E2E Partner <timestamp>-<random>`), so parallel or repeated runs never
collide and never depend on another run's leftover data. The Partner the
lifecycle test updates is always the one it just created — see the comment
in `partner-lifecycle.spec.ts` for the reasoning (an update that landed on an
arbitrary pre-existing record would be non-deterministic and could corrupt
data other runs rely on).

**Persistence verification, not optimistic-UI verification.** After Save,
the test forces `page.reload()` before re-checking the Partner — a fresh
fetch from the backend, not the in-memory state the UI already had. The same
principle governs _what_ gets asserted post-update: the list table doesn't
surface Type or Description, so the test reopens the (freshly re-fetched)
Edit form itself to confirm every field, not just the ones visible in the
table.

**Config over hardcoding.** `BASE_URL` and credentials come from environment
variables (`.env` locally, GitHub Secrets in CI) via `dotenv`, never
hardcoded — the same suite can point at another environment by swapping one
file.

**Headed locally, headless on CI, maximized window.** `process.env.CI` (set
automatically by GitHub Actions) is the single switch; no separate config
files to keep in sync.

**Debuggability & observability.** Three artifacts, captured only on
failure/retry so passing runs stay cheap: a Playwright **trace** (full
step-by-step timeline with DOM snapshots and network), a **screenshot**, and
a **video**. The reporter is `list` (live console feedback while a run is in
progress) plus `html` (the artifact a human opens afterwards) — never
auto-opening, so CI doesn't try to launch a browser and a local run doesn't
surprise you with a popup every time. `test.step()` names every phase of the
lifecycle flow (Log in / Navigate / Create / Validate / Update / Validate
persisted), so both the console output and the HTML report read as a
narrative, not a wall of individual assertions — this is also what makes the
single-flow test debuggable despite covering six logical steps: a failure
points at the exact step, not just "the test failed".

**Code quality tooling.** TypeScript `strict` (plus
`noUncheckedIndexedAccess`, which caught a real possible-`undefined` array
access during setup — see `tests/partner-lifecycle.spec.ts`), ESLint
(`typescript-eslint` + `eslint-plugin-playwright` for automation-specific
rules like flagging conditional logic in tests) and Prettier. All three run
as their own fast CI job (`quality`) that gates the — much slower — `test`
job, so a lint or type error fails in seconds, not after a multi-minute
Playwright run.

## Assumptions

- The "Partner" entity's required fields, as observed on `dev`: Name, Type
  (Service/Insurer), Services (multi-select), Subscription plan, Address,
  Telephone, Contact person, Description, Logo.
- "Validate that changes have been persisted correctly" means proven against
  a fresh backend fetch (page reload), not the UI's optimistic state — see
  above.
- Address and Logo are exercised (both are required fields, so the form is
  filled with real values) but not asserted field-by-field after persistence:
  Address is a free-text Places Autocomplete result with no fixed expected
  string to compare against, and Logo has no text representation to assert
  without visual diffing — a deliberate scope cut, not an oversight (see
  below for how I'd close it).
- `dev.admin.avtoikonom.com` is a disposable QA sandbox safe to write test
  data into — the account list already contained hundreds of prior
  `QA E2E Partner ...` records when this project started, consistent with
  that assumption.
- Subscription plan is selected (first available tier on create, a different
  one on update) to satisfy the required field, but not asserted by exact
  value: every tier in this environment's seed data renders under the same
  visible label, so no assertion could meaningfully distinguish "changed" —
  documented in `PartnersPage.expectFormMatches`.

## What I'd improve given more time

- **API-level verification alongside the UI check.** Sniffing the app's own
  network calls surfaced a `dev.api.avtoikonom.com` backend; a
  `request.get()` against it (reusing the browser's auth) would prove
  persistence independent of the UI layer entirely, and would be far faster
  than reopening the Edit dialog for a full field-by-field read-back.
- **Test data cleanup.** Nothing here deletes the Partners it creates — fine
  for a one-off exercise, not for a suite run hundreds of times a day, where
  it would keep bloating the target environment. I'd add an
  after-each/teardown step (or a scheduled cleanup job) deleting anything
  matching the `QA E2E Partner ...` naming convention older than N days.
- **Visual/byte-level assertion for the Logo field**, e.g. comparing the
  uploaded file's hash against what the persisted `<img src>` resolves to,
  to close the one field the current suite exercises but doesn't verify.
- **Auth via API, not UI, for setup.** Logging in through the UI on every
  test is realistic for the one test that verifies login itself, but is dead
  weight to repeat before every other test as the suite grows. I'd add a
  Playwright `storageState` fixture that logs in once and reuses the session,
  and keep the from-scratch UI login only in `login.spec.ts`.
- **Cross-browser/device matrix** (Firefox, WebKit, a mobile viewport) —
  scoped to Chromium only here since the whole exercise runs against one
  real, slow environment and breadth wasn't the goal.
- **Component-level negative/validation tests** — required-field
  validation messages, invalid phone/email formats, duplicate-name handling
  — the current suite is a happy-path lifecycle by design.
- **Secrets via the CI provider's native secret store** is already how this
  is wired (GitHub Secrets); in a real org I'd back it with a proper vault
  (e.g. 1Password/Vault CI integration) instead of raw repo secrets.
- **Sharding** (`--shard`) once the suite grows past a handful of specs, to
  keep CI wall-clock flat instead of linear in test count.

## CI

`.github/workflows/playwright.yml` runs on push/PR to `main`/`master` and on
manual dispatch, as two jobs:

1. **`quality`** — `format:check`, `lint`, `typecheck`. Fails fast, before
   spending CI minutes on a browser run.
2. **`test`** (needs `quality`) — installs Chromium (browser binaries cached
   by `package-lock.json` hash), runs the suite, and uploads the HTML report
   (always) plus traces/screenshots/videos (on failure) as build artifacts.

It expects `BASE_URL`, `ADMIN_EMAIL`, and `ADMIN_PASSWORD` as repository
secrets — without them, the credentialed tests skip themselves rather than
failing red, so the pipeline stays informative either way.
